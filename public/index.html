COST & USAGE

SIREN tracks two separate Claude meters. API Tokens are billed to the API key in .env every time an action below runs. Claude Usage measures Claude Code development sessions on this machine — it is not billed per token and no in-app action consumes it.

Claude API Tokens — billed per action

Shown as the API Cost tile in PULSE and the API Usage panel in ENGAGE. Pricing per million tokens: Sonnet 4.6 $3 in / $15 out · Haiku 4.5 $1 in / $5 out.

Every action above is metered server-side as it runs. The PULSE API Cost tile shows the current month (matching the Claude console's “spend this month”) with the all-time total beneath it.

Console Sync — credit balance & monthly spend

The Anthropic API doesn't expose your credit balance, so enter the current values from console.anthropic.com once. SIREN's meter advances both from there: spend counts up, balance counts down. Re-sync any time (e.g. after adding credits).

Claude Usage — development sessions

Shown as the Claude Usage tile in PULSE. It scans local Claude Code session transcripts (~/.claude/projects) and prices the tokens at API-equivalent rates. This measures time spent building SIREN with Claude Code — it is covered by the Claude subscription, not the API key, and nothing you do inside the app adds to it. Each machine shows its own local sessions.

DEV SYNC

SIREN uses Turso — a hosted SQLite database. Both machines point at the same cloud DB via .env. One-time setup below.

Step 1 — Create a Turso database (once)
# Install Turso CLI (Mac/Linux)
brew install tursodatabase/tap/turso

turso auth login
turso db create siren

# Get your credentials
turso db show siren --url
turso db tokens create siren
Step 2 — Add to .env on both machines
TURSO_DATABASE_URL=libsql://siren-yourname.turso.io
TURSO_AUTH_TOKEN=your-token-here
.env is gitignored — add these lines to the existing file on each machine.
Step 3 — Push existing data from this PC (once)
npm run db:push
Copies all rows from the local siren.db to Turso. Only needed once.
Step 4 — Start normally on any machine
npm start
Both machines read and write the same database. No syncing required.
Without Turso configured
Falls back to file:siren.db automatically — local development still works with no setup.

SPICED Framework Winning by Design · 6 components · built across the full deal lifecycle ▶
SPICED is not completed in a single meeting — it is assembled incrementally across the life of a deal. Grading reflects whether each component was addressed at the right stage, not just whether it was ever mentioned.
S
Situation
Meeting 1 Expected in full on the very first call.
The basic facts about the buyer's business — team size, tools in place, industry context, existing workflows, and current security posture. This is the foundation everything else builds on. A rep who reaches the Demo stage without a clear Situation picture is penalized.
P
Pain
Early — Discovery The primary driver for every call that follows.
The main problem that brought the buyer to you, in their words — not assumed or projected. Superficial pain ("we need better security") doesn't count. Grading looks for specificity: what exactly is broken, who feels it, and why fixing it matters now. Pain identified in discovery should be re-confirmed on every subsequent call.
I
Impact
Mid-deal — Demo stage Emerges as the prospect sees your value.
How the pain hurts their money, time, or risk exposure if left unresolved. Quantified when possible — cost per incident, headcount burden, compliance fines, audit failures. Impact is what converts interest into urgency. Reps who skip to Impact before Pain is established lose credibility; reps who never quantify Impact lose the Proposal.
C
Critical Event
Mid-stage Must be identified before Proposal — without it, deals stall.
The hard deadline or forcing event that makes solving the problem non-optional — a contract renewal, an upcoming audit, a board commitment, a recent breach, a compliance deadline. If the rep cannot name a Critical Event by the Demo stage, grading reflects that as a qualification gap. Deals without a Critical Event have no close date.
E
Evolution
Ongoing Tracked across every call as the buying committee shifts.
How the deal and buying team evolve — who else enters the conversation, how internal dynamics shift, and how the decision process changes over time. New stakeholders introduced late without preparation are a deal risk. Reps who track Evolution proactively surface blockers before they become fatal. Graded on whether the rep notices and responds to changes — not just whether they asked once.
D
Decision
Late-stage — Proposal/Close Named decision-maker and process confirmed before contract.
Who makes the final choice and exactly how they buy — named decision-maker, procurement process, legal/IT sign-off requirements, and the criteria they will use to choose. A rep who reaches the close without knowing who signs is graded as unqualified. Decision criteria must be known before the Proposal is presented so value can be framed against what actually matters to the buyer.
